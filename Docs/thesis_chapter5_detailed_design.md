# 第五章 系统详细设计与实现

第四章已经说明了系统的总体架构，也就是系统大体分成哪些层、各层之间怎样协作。本章则进一步展开系统内部的实现细节。换句话说，第四章回答的是“系统整体长什么样”，第五章回答的是“系统到底是怎么跑起来的”。一个工业异常检测系统如果只停留在总体架构层面，显然还不够。用户上传一张图片之后，系统怎样接收任务？怎样判断要不要调用视觉模型？怎样使用 RAG？怎样保存上下文？这些问题都需要在详细设计中说清楚。

本章将按照系统模块展开说明，主要包括用户交互模块、API 与任务运行模块、LangGraph 图编排模块、多 Agent 协作模块、视觉检测模块、RAG 知识库模块、状态记忆模块以及报告生成模块。每个模块都围绕“为什么需要这个模块、它接收什么输入、内部如何处理、最终输出什么结果”这条线索进行介绍。

## 5.1 用户交互模块设计与实现

用户交互模块是系统最外层的部分，也是用户真正能看到、能操作的部分。对于一个检测系统来说，前端页面不能只是简单地放一个上传按钮和一个返回结果区域。因为本系统不仅要完成首轮检测，还要支持继续追问、人工澄清、生成报告、查看热力图、观察多 Agent 执行过程以及主动构建 RAG 知识库。用户如果看不到这些过程，就很难理解系统为什么给出这样的结论。

本系统的前端采用单页工作台形式实现，对应项目中的 `web/index.html` 文件。页面整体围绕“检测任务”展开，主要划分为任务配置区、RAG 知识库区、异常摘要区、待澄清信息区、报告展示区、多 Agent 时间线区和对话输入区。这样的设计使用户在一个页面内就可以完成从图片上传到结果分析的完整流程。

在任务配置区，用户需要输入设备 ID，并上传待检测图片。系统支持多种视觉检测后端，包括 Qwen 通用视觉模型、PatchCore 本地异常检测算法以及专业视觉检测服务。为什么要提供多个后端？原因很简单：不同检测场景适合的模型并不一样。对于已经训练过的固定类别，PatchCore 能给出更稳定的热力图；对于没有训练过的类别，通用视觉模型可以先做开放式理解；如果后续接入专业检测服务，也可以通过统一工具接口进行调用。

RAG 知识库区域用于让用户直接在前端触发知识库构建。传统做法可能需要在终端中输入命令，但这种方式对普通用户并不友好。用户为什么一定要记住一长串 curl 命令呢？因此系统在前端提供了数据集路径输入、是否包含正常样本选项、开始建库按钮和进度展示区域。用户点击“开始建库”后，前端调用 `/v1/rag/build/start` 接口启动异步建库任务，并周期性查询 `/v1/rag/build/status/{task_id}` 获取进度。页面会显示当前阶段、进度百分比、已处理样本数和向量数量。

结果展示区负责呈现当前回答、异常摘要和结构化分析内容。如果视觉后端使用 PatchCore，系统还会返回热力图、叠加图和 mask 路径，前端可以在原图、边界框、热力图和叠加图之间切换。这样用户不仅知道“系统说有异常”，还能看到“异常大概在哪里”。对于工业检测任务来说，这一点很重要。只给一句“检测到异常”，并不能帮助操作人员判断是否需要复检；但如果能看到异常区域和热力图，结论就更容易被理解。

多 Agent 时间线是前端中比较有特点的一个部分。系统执行过程中会产生计划创建、步骤开始、步骤完成、步骤失败等事件，前端将这些事件渲染成时间线。用户可以看到本次任务到底调用了哪些 Agent，例如是否调用了 VisionAgent、KnowledgeAgent 或 ReportAgent。如果任务失败，也可以从时间线中看到失败发生在哪一步。正如一句常见的软件工程说法：“看不见的系统，就很难被调试。”多 Agent 系统尤其如此，因为它的执行过程比单模型调用复杂得多。

追问和澄清交互通过同一个对话输入区完成。首轮检测时，用户上传图片并点击开始检测；任务创建后，用户可以继续输入问题发起追问。如果系统进入待澄清状态，输入框中的内容则会作为用户补充信息提交给后端。前端根据任务是否已经创建、是否处于 pending 状态来控制“发送追问”和“提交澄清”按钮的可用状态，避免用户在错误阶段提交错误类型的请求。

## 5.2 API 与任务运行模块设计与实现

API 与任务运行模块是前端与后端系统之间的桥梁。前端页面上的每一次点击，最终都要变成后端能够理解的任务请求。该模块主要由 `app/api/main.py` 和 `app/services/` 下的服务文件实现。

后端使用 FastAPI 提供接口。系统中的主要接口包括 `/v1/stream`、`/v1/detect`、`/v1/chat`、`/v1/continue`、`/v1/generate_report`、`/v1/rag/build/start`、`/v1/rag/query` 和 `/v1/patchcore/categories` 等。其中 `/v1/stream` 是前端检测流程最常用的接口，它通过 Server-Sent Events 将系统执行过程实时推送给前端。相比普通 HTTP 请求一次性返回结果，流式接口更适合多 Agent 系统，因为用户可以看到系统正在执行哪一步，而不是只能等待最终答案。

为了让不同接口和不同 Agent 能够处理统一的数据，系统定义了 `DetectionTask` 作为任务输入结构。一个 `DetectionTask` 中包含任务 ID、设备 ID、开始时间、结束时间、用户问题和参数字段。参数字段中可以保存图像 base64、图像 MIME 类型、视觉后端类型、PatchCore 类别、阈值、对象上下文和用户 ID 等内容。这样设计的好处是，API 层不需要把所有参数都拆散传给每个模块，Agent 和工具层只要读取同一个任务对象即可。

首轮检测时，任务运行模块会根据前端提交的信息构造新的 `DetectionTask`，并创建新的 `DetectionState` 作为 LangGraph 的初始状态。追问时则不同。追问并不是重新开始一个任务，而是要复用上一轮检测的上下文。例如用户问“这个异常严重吗”，系统应该基于上一轮图片和检测结果回答，而不是要求用户重新上传图片。因此系统会根据 task_id 读取历史状态，更新当前问题，同时保留上一轮视觉结果、RAG 结果和共享上下文。

追问状态恢复对应 `app/services/state_rehydration.py` 中的逻辑。这里有一个容易忽略的问题：追问时如果不清空上一轮回答，系统可能会直接返回旧答案，看起来就像“没有思考”。因此系统在准备追问状态时会清空 `context.answer`，并记录 `is_followup`、`latest_question` 和 `followup_question` 等字段。这样 AnswerNode 必须针对当前问题重新生成回答。

流式输出由 `app/services/streaming.py` 实现。系统会监听 LangGraph 执行过程中的事件，并将其转换成前端可识别的数据格式。常见事件包括节点开始、模型输出、执行快照、执行事件和最终结果。最终结果中不仅包含回答文本和异常列表，还包含执行计划、step 状态、Agent trace、MMAD 分析结果和 few-shot 信息。前端正是依靠这些元数据，才能展示完整的多 Agent 时间线和结构化分析结果。

## 5.3 LangGraph 图编排模块设计与实现

如果说 Agent 是系统中的“执行者”，那么 LangGraph 就是这些执行者的“流程图”。本系统使用 LangGraph 构建任务状态图，对应项目中的 `app/core/graph.py`。它定义了任务从开始到结束会经过哪些节点，以及在什么条件下跳转到不同分支。

当前系统的主流程可以概括为：

```text
load_data
→ supervisor_plan
→ supervisor_execute
→ supervisor_merge
→ self_reflect
→ answer
```

`load_data` 节点负责确认任务数据已经存在，并在状态中记录数据加载完成。这个节点本身逻辑并不复杂，但它让后续流程有了一个明确的起点。

`supervisor_plan` 节点用于生成执行计划。它会调用 SupervisorAgent，根据当前任务是否包含图像、用户问题是否涉及知识分析、是否存在失败重试状态等信息，决定接下来应该调用哪些专家 Agent。比如有新图片时通常需要 VisionAgent；如果用户问“为什么会这样”或“有没有相似案例”，就需要 KnowledgeAgent；如果用户要求生成报告，则需要 ReportAgent。

`supervisor_execute` 节点负责执行计划中的 Agent step。每个 step 都有自己的 ID、Agent 名称、执行目标和依赖关系。如果某个 step 依赖另一个 step 的结果，系统会等依赖成功后再执行它。如果依赖失败，当前 step 也会被标记为失败。

`supervisor_merge` 节点负责合并不同 Agent 的输出。VisionAgent 的结果会进入 `shared_context.vision`，KnowledgeAgent 的结果会进入 `shared_context.knowledge`，ReportAgent 的结果会进入 `shared_context.report`。合并阶段还会根据已有视觉和知识结果生成 MMAD 七任务分析结构。

`self_reflect` 节点用于判断当前结果是否可靠。为什么需要这个节点？因为模型或工具并不总是成功执行。如果视觉检测失败，系统不能把“没有检测结果”当成“没有异常”。self_reflect 节点会检查失败 step、置信度和异常信息，如果发现结果不可靠，会设置 retry_target，让系统重新执行对应 Agent。

`wait_user` 节点用于处理人工澄清。当系统判断需要用户补充信息时，会生成待澄清问题，并将任务置为 pending 状态。用户提交补充信息后，系统再继续执行。

`answer` 节点负责生成最终回答。它会综合当前检测结果、RAG 知识上下文、记忆上下文、对话历史和 MMAD 分析结果，生成面向用户的中文诊断内容。

该图编排模块的一个关键点是条件路由。系统不是固定执行所有节点，而是根据状态决定下一步。例如，执行计划为空时可以跳过 Agent 执行；需要用户澄清时进入 wait_user；反思节点要求重试时返回 supervisor_plan；用户请求报告时进入 report 节点。这种状态图方式比简单的 if-else 调用链更清晰，也更适合多 Agent 任务。

## 5.4 多 Agent 协作模块设计与实现

多 Agent 协作模块是系统的核心部分。它并不是把所有功能都交给一个大模型，而是将任务拆分给不同职责的 Agent。这样做的好处是什么？一方面可以让每个 Agent 的职责更清晰，另一方面也便于后续替换或扩展某个能力。

SupervisorAgent 是主控 Agent，对应 `app/agents/supervisor/agent.py`。它的职责不是直接做检测，而是决定“下一步该让谁来做”。如果任务中有图片输入，通常需要调用 VisionAgent；如果用户问题包含原因、风险、建议、维修、RAG 或相似案例等关键词，就需要调用 KnowledgeAgent；如果存在失败重试状态，则优先规划 retry_target 对应的 Agent；如果用户要求报告，则调用 ReportAgent。可以说 SupervisorAgent 更像一个调度员，它负责把任务分配给合适的专家。

VisionAgent 是视觉检测 Agent，对应 `app/agents/vision/agent.py`。它接收 `DetectionTask`，并调用图像异常检测工具。VisionAgent 本身不绑定某一个模型，而是通过 `ImageAnomalyDetectionTool` 根据参数选择 Qwen、PatchCore 或专业检测服务。执行完成后，VisionAgent 会将结果统一封装为 AgentEnvelope，其中包含异常列表、元数据、热力图路径、类别信息和执行状态。

KnowledgeAgent 是知识分析 Agent。它会根据当前视觉检测结果和用户问题构造查询文本，然后调用 RAG 检索相似案例。检索结果不仅用于展示相似样本，还会进一步生成缺陷成因、风险提示、维修建议、产品结构和功能影响等内容。也就是说，KnowledgeAgent 让系统从“看图识别异常”进一步扩展到“解释异常为什么重要”。

ClarificationAgent 用于处理不确定性。如果系统无法可靠判断异常位置、异常类型或用户意图，它会生成澄清问题。与其让系统在不确定时强行回答，不如主动问用户一句：“请确认异常是否位于图像右下区域？”这种设计更符合实际工业检测过程，因为很多场景本身就需要人工复核。

ReportAgent 用于生成完整诊断报告。最终回答通常偏简短，适合即时交互；而报告需要更完整地组织异常信息、结构化分析、风险提示和建议动作。ReportAgent 会复用当前任务中的视觉结果、知识结果、MMAD 分析和对话历史，生成更适合保存归档的内容。

多 Agent 协作层通过统一的执行计划、共享上下文和 AgentEnvelope 将这些 Agent 连接起来。每个 Agent 都只关注自己的任务，系统则通过 supervisor_merge 节点将它们的输出整合为统一结果。

## 5.5 视觉检测模块设计与实现

视觉检测模块是系统最基础也最关键的能力。如果视觉检测不可靠，后续的知识分析和报告生成都会受到影响。本系统同时支持 Qwen 通用视觉检测、PatchCore 本地异常检测和专业 HTTP 检测服务。

Qwen 通用视觉检测对应 `app/tools/image_anomaly_detection.py` 中的 Qwen 工具。系统会将用户上传的图片转换为 base64，并构造结构化 prompt 发送给 Qwen。模型需要返回 JSON 格式结果，包括异常类型、置信分数、描述、边界框和粗略位置。JSON 格式的好处是便于后续程序解析，而不是只能处理自然语言描述。

不过，通用视觉模型用于工业异常检测时存在一个问题：它容易把正常纹理、反光、阴影或边缘当成异常。比如一张 MVTec 的 good 图片，本来是正常样本，但模型可能会因为局部反光而返回一个“疑似异常”。这显然会影响系统可信度。为了解决这个问题，系统从三个方面进行了误报抑制。

第一，系统在 prompt 中明确要求：如果图像接近正常样本，应返回 `anomalies: []`，不要强行寻找异常。第二，系统在 VisionAgent 执行前尝试从 RAG 中检索正常和异常 few-shot 样本，并将这些参考样本注入 prompt，使 Qwen 能够比较当前图像更接近正常样本还是异常样本。第三，系统设置 `APP_QWEN_MIN_ANOMALY_SCORE` 阈值，低于阈值的候选不会进入最终异常列表。同时，如果候选描述中包含“疑似、反光、阴影、边缘、纹理、噪声”等弱证据，也会被过滤。这些被过滤的候选不会直接判为异常，但会保存在 metadata 中，方便后续排查。

PatchCore 用于固定类别异常检测，对应 `app/tools/patchcore_detection.py` 和 `scripts/patchcore_train.py`。PatchCore 的思路与 Qwen 不同。它不是通过大模型理解图像，而是先用正常样本建立 memory bank，再在推理时比较输入图像 patch 特征与正常特征之间的距离。距离越大，越可能是异常区域。系统根据异常分数生成热力图，再根据阈值生成 mask，并从 mask 中提取连通区域作为 bbox。

PatchCore 的优势是适合固定类别，尤其是 MVTec 这类工业异常检测数据集。它能给出比较直观的热力图结果。但它也有局限：没有训练过的类别不能直接使用。因此系统增加了类别检查逻辑，只有当对应类别存在 memory bank 和 metadata 时，才允许使用 PatchCore；否则前端会提示用户切换到 Qwen 或先训练该类别。

## 5.6 RAG 知识库模块设计与实现

RAG 知识库模块用于为系统提供外部知识和样本参考。没有 RAG 时，Qwen 只能依靠自身的通用视觉理解；有了 RAG 后，系统可以告诉模型：“这里有一些同类别正常样本，也有一些相似异常样本，你可以参考它们再判断。”这对工业异常检测尤其重要，因为正常样本的外观往往与产品类别、拍摄环境和工艺状态有关。

RAG 建库的第一步是数据集扫描，对应 `app/rag/dataset_analyzer.py` 中的 DatasetAnalyzer。系统按照 MVTec 数据集目录结构识别正常和异常样本。其中 `train/good` 和 `test/good` 会被标记为正常样本，`test/<defect_type>` 会被标记为异常样本。如果存在 ground_truth mask，系统还会根据 mask 面积估计异常严重程度。

第二步是生成样本文本描述。图像样本本身不能直接用于文本检索，因此系统通过 AnomalyTextGenerator 为样本生成描述，例如类别、缺陷类型、是否异常、严重程度等信息。随后 VectorStore 调用多模态 embedding 模型，将文本和图像信息转换为向量，并写入 Chroma 向量库。

运行时，RAG 主要有两条使用路径。第一条路径发生在 VisionAgent 执行前。系统通过 `_build_visual_fewshot` 尝试检索与当前任务相似的 normal 和 anomaly 样本，再由 FewShotSelector 筛选正常样本和异常样本，由 FewShotPromptBuilder 构造 few-shot_context。这个上下文会被注入 Qwen prompt，用于降低正常图误报。

第二条路径发生在 KnowledgeAgent 执行时。如果用户询问原因、风险、建议、维修或相似案例，SupervisorAgent 会规划 KnowledgeAgent。KnowledgeAgent 根据当前异常结果构造查询文本，从 RAG 中检索相似案例，并生成缺陷分析和产品分析。缺陷分析包括可能成因、风险提示、建议动作和相似案例；产品分析包括产品结构、关键部件和功能影响。

RAG 并不是每次都强制执行。如果知识库没有构建、向量库为空或检索失败，系统不会中断主检测流程，而是继续执行视觉检测。这种设计保证了系统的可用性：有 RAG 时结果更专业，没有 RAG 时系统仍然可以完成基本检测。

## 5.7 状态记忆模块设计与实现

状态记忆模块用于解决一个实际问题：系统怎样记住上一轮发生了什么？如果用户首轮检测后继续问“为什么会这样”，系统必须知道上一轮检测的是哪张图、检测到了哪些异常、是否调用过 RAG、已经生成过哪些分析结果。否则，多轮对话就会变成互不相关的单轮问答。

系统的核心状态对象是 `DetectionState`，对应 `app/memory/state.py`。它保存任务信息、检测结果、上下文、共享上下文、Agent 输出、Agent trace、执行计划、step 状态、执行事件、对话历史、对话摘要和失败重试信息等内容。

为了让状态结构更清晰，系统将状态访问分为三个运行视图。`task_runtime` 保存任务输入、对话历史、用户回复、当前阶段和报告请求；`orchestration_runtime` 保存执行计划、当前激活 Agent、step 状态、重试次数、执行事件、失败 step 和反思决策；`domain_runtime` 保存检测结果、共享上下文、工具调用、工具输出和 Agent 输出。这样做可以避免所有模块都直接操作顶层状态字段，使任务信息、编排信息和领域结果之间的边界更加清楚。

Checkpoint 用于保存任务运行状态。系统支持 memory 和 postgres 两类 checkpoint 后端。开发调试时可以使用 memory，部署或需要持久化时可以使用 postgres。任务恢复、追问、澄清继续和报告生成都依赖 checkpoint 中保存的状态。

对话历史压缩用于处理长对话问题。如果用户持续追问，完整对话历史会越来越长，直接放入模型上下文会增加成本，也可能影响回答质量。因此系统会将较早的对话压缩为 conversation_summary，同时保留最近若干轮对话。这样既能保留历史信息，又不会让上下文无限增长。

系统还包含短期记忆、长期记忆和工具记忆。短期记忆用于记录同一设备近期的异常情况；长期记忆用于保存更长周期的历史信息；工具记忆用于记录工具调用输入、输出和效果。AnswerNode 在生成最终回答时，会读取这些记忆上下文，使回答不只依赖当前一张图片。

## 5.8 报告生成与结构化诊断模块设计与实现

报告生成与结构化诊断模块用于将系统结果整理成更完整的诊断输出。对于用户来说，一次检测后可能只需要一句回答；但对于论文系统和工业场景来说，仅有一句回答还不够，还需要结构化结果和完整报告。

系统引入了 MMAD 七任务分析结构，对应 `app/analysis/mmad_pipeline.py`。七个任务包括异常判别、缺陷分类、缺陷定位、缺陷描述、缺陷分析、产品分类和产品分析。系统会根据视觉检测结果和知识分析结果填充这些字段。例如，异常判别用于说明是否存在异常，缺陷定位用于记录异常位置和热力图信息，缺陷分析用于记录可能成因和风险，产品分析用于说明异常可能影响的产品部件。

AnswerNode 对应 `app/core/answer_node.py`，负责生成最终中文回答。它会综合当前 DetectionResult、RAG prompt_context、memory context、MMAD 七任务分析和对话历史。这里有一个重要原则：如果视觉检测失败，系统不能回答“正常”。因此 AnswerNode 对失败结果做了特殊处理，会明确提示本次检测没有得到可靠结果，而不是把空异常列表误解为正常。

ReportAgent 用于生成完整报告。报告会复用当前任务中的视觉结果、知识分析、MMAD 分析和对话历史。相比即时回答，报告内容更完整，适合保存、复核和归档。对于工业异常检测场景，报告不仅要说明检测结果，还要说明证据、风险和建议，这也是 ReportAgent 存在的意义。

## 5.9 本章小结

本章从实现角度介绍了系统各模块的详细设计。用户交互模块负责把检测、追问、RAG 建库和结果展示整合到一个工作台中；API 与任务运行模块负责将前端请求转换为统一任务，并通过流式方式返回执行过程；LangGraph 图编排模块负责控制任务节点和条件路由；多 Agent 协作模块负责将视觉检测、知识分析、澄清和报告生成拆分给不同 Agent；视觉检测模块实现了 Qwen、PatchCore 和专业检测后端的统一接入；RAG 知识库模块提供正常样本、异常样本和相似案例支持；状态记忆模块保证系统能够进行多轮追问和任务恢复；报告生成与结构化诊断模块则将多源结果组织成最终回答和完整报告。

整体来看，本系统不是简单地“上传图片、调用模型、返回文本”，而是围绕工业异常检测任务构建了一条较完整的诊断链路。它既有视觉检测，也有知识检索；既有自动回答，也有人工澄清；既能给出即时结果，也能生成报告。这样的设计使系统更接近真实应用中的检测流程，也为后续实验验证和功能扩展提供了基础。
