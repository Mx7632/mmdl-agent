# MMDL-Agent 项目介绍与交接说明

这份文档是我在毕业交接时用于介绍本项目的说明材料。它的重点不是只列技术名词，而是让老师、同学或后续接手的人能够快速理解：这个项目做了什么、为什么这样做、现在能运行到哪一步，以及后续应该从哪里继续。

## 1. 项目一句话介绍

我的毕业设计项目是一个面向工业视觉质检场景的异常检测 Agent 系统。

它不是单独实现某一个异常检测算法，而是把图像异常检测、热力图定位、多 Agent 协同分析、RAG 知识检索、追问续接和报告生成整合到一个可以运行、可以演示、可以继续扩展的系统里。

用户上传一张工业图像后，系统可以完成以下流程：

- 判断图像中是否存在异常。
- 给出异常区域、异常分数和定位结果。
- 生成热力图、叠加图或掩码图，方便观察异常位置。
- 通过 Agent 流程组织视觉分析、知识解释和结果总结。
- 支持用户继续追问，而不是每次都从零开始。
- 在需要时生成结构化的检测说明或报告。

## 2. 我为什么做这个项目

工业异常检测如果只停留在“模型判断有无异常”，实际使用价值是不够的。真实质检场景里，使用者更关心的是：

- 异常在哪里。
- 异常大概属于什么问题。
- 模型为什么这么判断。
- 有没有类似样本或知识可以参考。
- 检测结果能不能被记录、追问和整理成报告。

所以我把项目目标定为一个完整的工业异常诊断辅助系统，而不是一个孤立的算法脚本。异常检测算法负责给出视觉证据，Agent 和 RAG 负责把结果组织成更容易理解、可追踪、可继续分析的系统流程。

## 3. 当前系统由哪些部分组成

项目主仓库是 `MMDL-Agent`，主要目录如下：

- `app/`：后端核心代码，包括 FastAPI 接口、Agent 工作流、RAG 服务、工具调用和运行状态管理。
- `web/`：前端页面，用于图片上传、检测提交、热力图展示、Agent 时间线展示和会话记忆展示。
- `Docs/`：项目文档、运行说明、系统设计说明和论文相关材料。
- `scripts/`：数据导入、评估、论文材料处理和实验辅助脚本。
- `tests/`：接口测试、流程测试和关键功能验证。
- `data/`：运行时数据目录，主要保存上传文件、热力图、RAG 索引和运行缓存，不建议把大体积运行数据提交到 Git。

后端使用 FastAPI 作为服务入口，Agent 编排使用 LangChain 和 LangGraph，配置管理使用 Pydantic Settings，RAG 向量库使用 ChromaDB。

## 5. GRAD 算法在项目中的位置

老师给的 GRAD 算法不是直接塞进主后端里运行的，而是被我封装成了一个独立的 sidecar 服务。

这样做的好处是：

- GRAD 保留自己的训练环境、配置文件和权重路径。
- 主系统只需要通过 HTTP 调用 GRAD 服务。
- 后续如果要换权重、换类别或换算法，不需要大改主后端。
- 如果 GRAD 依赖的 PyTorch、CUDA、Python 版本和主系统不同，也比较容易隔离。

可以这样理解：

- GRAD 负责专业的图像异常定位。
- MMDL-Agent 负责接口封装、Agent 流程、前端展示、RAG 解释和报告生成。

目前 GRAD 相关的重要路径是：

```text
/root/autodl-tmp/gradcn
```

主项目服务器路径是：

```text
/root/autodl-tmp/mmad-agent
```

蕾丝数据集原始服务器路径是：

```text
/root/autodl-tmp/all/lace
```

蕾丝数据集转换后的 GRAD 数据路径是：

```text
/root/autodl-tmp/gradcn/data/Lace-AD
```

蕾丝 GRAD 权重路径是：

```text
/root/autodl-tmp/gradcn/experiments/exp/GRAD/LaceAD/checkpoints/ckpt_best.pth.tar
```

## 6. 项目怎么运行

接手人需要重点理解两个服务：一个是 GRAD 检测服务，一个是主后端服务。

第一步，启动 GRAD sidecar：

```bash
cd /root/autodl-tmp/mmad-agent
python -m uvicorn services.grad_local.app:app --host 0.0.0.0 --port 9011
```

第二步，启动主后端：

```bash
cd /root/autodl-tmp/mmad-agent
python -m uvicorn app.api.main:app --host 0.0.0.0 --port 8000
```

第三步，检查主服务健康状态：

```bash
curl http://127.0.0.1:8000/v1/system/health
```

如果返回结果中 `grad_sidecar` 是 `configured`，说明主项目已经识别到 GRAD 检测服务。

如果要直接检查 GRAD 服务：

```bash
curl http://127.0.0.1:9011/health
```

更完整的运行细节可以继续看：

- `Docs/runtime_guide.md`
- `Docs/grad_sidecar_runbook.md`
- `Docs/system_overview.md`

## 7. 我建议老师和接手人重点看什么

如果是老师了解项目，我建议重点看：

- 前端演示页面能否完成图片上传和检测。
- GRAD 或 PatchCore 是否能输出热力图定位。
- Agent 时间线是否能展示分析流程。
- RAG 和追问功能是否能说明“系统不是单次模型调用”。
- 检测结果是否能形成结构化解释。

如果是后续同学接手开发，我建议重点看：

- `app/api/main.py`：后端接口入口。
- `app/services/industrial_runtime.py`：任务、反馈、会话等运行状态保存。
- `app/tools/image_anomaly_detection.py`：视觉检测工具路由。
- `app/tools/grad_detection.py`：本地 GRAD 检测封装。
- `services/grad_local/app.py`：GRAD sidecar 服务入口。
- `web/index.html`：当前主要前端页面。
- `Docs/grad_sidecar_runbook.md`：GRAD 启动和排障说明。

## 8. 当前项目的价值

这个项目的价值主要体现在工程整合和可解释流程上。

第一，它不是只跑模型，而是形成了从图片上传、异常检测、热力图定位、Agent 分析、RAG 检索到结果展示的完整链路。

第二，它把传统异常检测算法和 Agent 系统结合起来，让检测结果不只是一个分数，而是可以被解释、追问和记录。

第三，它已经接入了老师给的 GRAD 算法，并且通过 sidecar 方式和主项目解耦，后续继续训练新权重或替换检测算法比较方便。

第四，它有前端演示页面，适合毕业答辩、项目展示和后续扩展。

## 9. 当前仍然存在的不足

这个项目目前更接近毕业设计原型系统，还不是生产级工业平台。后续仍有一些可以继续完善的地方：

- 不同类别的异常检测权重还需要继续训练和标定。
- GRAD、PatchCore 等检测结果的阈值还需要根据真实业务数据调整。
- RAG 知识库内容还可以继续补充真实工业案例。
- Agent 的解释内容可以进一步减少模板化表达。
- 前端页面可以继续优化交互体验和结果对比能力。
- 报告生成可以继续做成更完整的 PDF 或 Word 输出。
- 测试覆盖还可以继续补充，尤其是端到端流程测试。

## 10. 后续接手建议

如果后续继续做，我建议按三个方向推进。

第一，继续完善数据和模型。可以把更多工业类别数据整理成统一格式，分别训练 GRAD 或 PatchCore 权重，再补充类别配置和阈值。

第二，继续完善系统展示。重点优化前端结果页，让热力图、异常框、检测分数、Agent 分析和历史会话展示得更清楚。

第三，继续完善知识和报告。把真实缺陷类型、工艺背景、处理建议整理进 RAG 知识库，让系统输出更贴近工业质检人员的表达习惯。

## 11. 我向别人介绍时可以这样说

如果我要用一段话介绍这个项目，我会这样说：

> 我的毕业设计是一个工业异常检测 Agent 系统。它以 FastAPI 为后端，以前端页面作为交互入口，集成了 PatchCore 和老师提供的 GRAD 异常检测算法，并通过 LangGraph 组织多 Agent 协同流程。用户上传工业图像后，系统可以完成异常判断、热力图定位、知识检索、追问续接和报告生成。GRAD 算法已经被封装成独立检测服务接入主系统，并完成了 MVTec 和蕾丝数据集实验。后续接手者可以继续扩展数据集、训练更多类别权重，或者优化 Agent 的解释和报告生成能力。

如果是向老师介绍，我会强调：

> 这个项目的重点不是单独提出新算法，而是把异常检测算法接入一个完整的工业诊断 Agent 系统，让检测结果能够被定位、解释、追问和记录。

如果是向后续开发者介绍，我会强调：

> 接手时先跑通两个服务：GRAD sidecar 和主 FastAPI 后端；再从 `app/tools/`、`app/services/`、`web/` 和 `Docs/` 这几部分理解检测、状态保存、前端展示和运行文档。

## 12. 交接时我会提醒的注意事项

交接时我会特别提醒以下几点：

- 不要把 `.env`、API Key、模型权重、大数据集、ChromaDB 运行时文件提交到 Git。
- 修改配置时优先改 `.env`，不要在业务代码里硬编码路径或密钥。
- GRAD 的 Python、PyTorch、CUDA 环境可能和主项目不同，优先保持 sidecar 隔离运行。
- 训练新类别前，先确认数据是否整理成 GRAD 代码期望的目录和 JSON 格式。
- 改前端接口字段时，要同步检查后端 Pydantic schema 和 API 返回结构。
- 每次改完核心流程后，至少跑一次相关测试或手动请求验证。

这就是我对项目当前状态的整体介绍。后续如果有人接手，我建议先按运行文档把系统启动起来，再从一次完整图片检测流程入手理解代码，这样比直接从所有文件里找逻辑更容易。
